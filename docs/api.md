## 0. 通用约定

### 0.1 请求与响应基础

| 项 | 约定 |
|---|---|
| Base URL | `http://localhost:8080`（无 context-path） |
| 请求体 | `Content-Type: application/json`（文件上传用 `multipart/form-data`） |
| 响应体 | 恒为 `{"code": int, "msg": string, "data": any}` |
| 成功判定 | **`code == 0`**（不是 HTTP 状态码） |

#### ⚠️ HTTP 状态码 ≠ 响应体业务 code

**本项目所有业务错误都走 `GlobalExceptionHandler`，统一返回 `HTTP 200` + 响应体 `code != 0`。**

| | HTTP 状态码 | 响应体 `code` |
|---|---|---|
| 成功 | `200` | `0` |
| 参数校验失败 | `200` | `400` |
| 未登录 / 无权限 | `200`（按代码推断） | `401` / `403` |
| 业务异常（商品不存在等） | `200` | `2001`… |
| 系统异常 | `200` | `500` |

**验证情况**：
- ✅✓ **业务异常 → HTTP 200**：已实测。压测脚本以 `statusCode != 200` 判定失败，4000 次请求（含大量 `2003` 业务错误）**失败 0 次**
- ⚠️ **401 / 403 → HTTP 200**：**未实测**，按代码（同一个 `@RestControllerAdvice`）推断。前端**不要用 HTTP 状态码判断登录态，要读 `code`**

### 0.2 鉴权与访问控制

#### 当前真实配置（`WebConfig` + `LoginInterceptor`）

```
拦截范围：/**（全部路径）
放行白名单（仅 3 条）：
  /user/login
  /user/register
  /error
额外放行：非 HandlerMethod 的请求（静态资源 /upload/**）—— 在拦截器里按 handler 类型判断
```

#### ⚠️ 由此得出的硬结论（与旧文档矛盾，已修正）

**当前配置下，下列接口全部【需要登录】，不是匿名公开：**

| 接口 | 旧文档标注 | **实际** |
|---|---|---|
| `GET /product/list` | 公开 | **需登录** |
| `GET /product/search` | 公开 | **需登录** |
| `GET /product/{id}` | 需登录 | 需登录 ✅ |
| `GET /category/list` | 公开 | **需登录** |
| `GET /hello` | 公开 | **需登录** |

> **全文其余部分一律按"除白名单外全部需登录"执行**，不再逐条标"公开"。

#### ✅ 已定（2026-10-10）：维持「全部需登录」，**不开放匿名浏览**

**理由**：
1. 与拦截器现状一致 —— **零代码改动**
2. `getDetail` 的浏览历史依赖登录态（`UserContext`），开放匿名会引入 NPE 风险
3. 前端（D10）本来就要求先登录再浏览

**备查：将来若真要开放，必须同时改 3 处**（缺一处就出问题）：

| # | 位置 | 改什么 | 不改的后果 |
|---|---|---|---|
| ① | `WebConfig` | 把商品列表/搜索/分类/详情加入白名单 | 匿名访问直接 401 |
| ② | `LoginInterceptor` | 无 token 时**不抛异常**，放行为匿名（`UserContext` 为空） | 仍 401 |
| ③ | `ProductServiceImpl.getDetail` | `recordHistory` 在未登录时**跳过** | ⚠️ **NPE**（`UserContext.get().getId()` 直接解引用） |

> ⚠️ **③ 是硬性依赖** —— 现在的代码在匿名访问详情时**必然 NPE**。"公开商品详情"不是改白名单就能完成的。

### 0.4 分页约定（统一）

**凡返回列表的接口，一律分页**（含计划中的接口），不保留"不分页"的例外。

| 项 | 约定 |
|---|---|
| 每页默认 | **10** |
| 每页最大 | **50**（传 > 50 时**截断为 50**，不报错；传 `null` 用默认 10） |
| 页码 | 从 **1** 开始；`< 1` → `400`（D8 补校验） |
| 排序 | **创建时间 DESC，时间相同时按 `id` DESC**（稳定排序） |
| 出参 | MyBatis-Plus `Page`：`{records, total, size, current, pages}` |

**入参形式**：
- `GET` 接口 → **查询字符串**（`?pageNum=1&pageSize=10`）
- `POST` 接口 → JSON body

⚠️ **D8 已补齐**：`pageNum < 1` → `400`（Controller 上 `@Validated` + `@Min(1)`）；
`pageSize > 50` → 在 Service 里 `Math.min` **截断为 50（不报错）**；
排序**全部带 id 兜底**（含 `price_asc` / `price_desc`）；
`keyword` 加 `@Size(max = 50)`；
不存在的 `categoryId` → `2016` 明确报错（不再静默返回空列表）。

### 0.6 订单状态流转

**⚠️ 必须区分「状态转换」与「触发原因」** —— 同一条边可以由不同原因触发。

**状态转换（边）：共 5 条**

```
待付款 ──①──→ 已付款 ──③──→ 已发货 ──⑤──→ 已完成
   │              │
   ②              ④
   ↓              ↓
       已取消（终态）
```

**触发原因：已实现 7 种 + D2 新增 1 种 = 8 种**

| 边 | 触发原因 | 谁 | 状态 |
|---|---|---|---|
| ① 待付款→已付款 | 支付（**模拟支付**） | 买家 | ✅✓ |
| ② 待付款→已取消 | 取消 | 买家 | ✅✓ |
| ② 待付款→已取消 | 取消 | 卖家 | ✅✓ |
| ② 待付款→已取消 | **超时关闭**（15 分钟） | **系统** | ⬜ D2 |
| ③ 已付款→已发货 | 发货 | 卖家 | ✅✓ |
| ④ 已付款→已取消 | 取消 | 买家 | ✅✓ |
| ④ 已付款→已取消 | 取消 | 卖家 | ✅✓ |
| ⑤ 已发货→已完成 | 确认收货 | 买家 | ✅✓ |

**明令禁止的转换**：

| 转换 | 为什么禁止 |
|---|---|
| 已发货 → 已取消 | 钱已付、货在路上。作废必须走**退款**，否则"已取消"语义崩（既含"没付钱作废"又含"付了钱作废"，无法判断要不要退钱） |
| 待付款 → 已发货（跳步） | 绕过付款 |
| 已完成 / 已取消 → 任何状态 | 终态 |
| 任意反向（已付款→待付款等） | 不允许回退 |

| 1002 | 用户不存在 | 2010 | 商品正在交易中 |
| 1003 | 用户名或密码错误 | 2011 | 订单未完成，暂不能评价 |
| 1004 | 原密码错误 | 2012 | 该订单已评价过 |

| 1007 | 文件上传失败 | 2016 | 分类不存在 |
| 2001 | 商品不存在 | 2014 | 商品已售出，不能下架 |

> ⚠️ **`400` 不是枚举，是全局异常处理器直接返回的**（参数校验 / 缺少必填参数 / 参数类型不对）。
> `404` 同理（访问不存在的路径）。D8 补齐了 `GlobalExceptionHandler` 里对应的 handler ——
> 在此之前这些情况**全被兜底成 `500`「服务器开小差了」**。

> ⚠️ **2014 与 2015 不要弄混**：`2014` 是「**商品**已售出不能下架」（管理员下架用）；
> `2015` 是「**用户**已被禁用」（枚举名 `USER_DISABLED`）。

**详情接口的缓存设计（已实测）**

```
GET /product/{id}
 ├─ Redis 命中真数据（TTL 30min）→ 直接返回，【不查询商品表】
 ├─ Redis 命中空值标记 ""（TTL 1min）→ 抛 2001，不查商品表（防穿透）
 └─ 未命中 → 查商品表 → 回填 / 写空值标记
```

⚠️ **"命中缓存 = 不查询商品表"** —— 精确表述。**不代表完全没有数据库访问**
（D6 内联卖家信息后还会查 user 表，见 §3.5）。

**缓存写入/失效：** `update` / `offline` / `delete` 三处在 `rows==0` 检查之后、`log` 之前 `delete` 缓存。

**压测数据（⚠️ 注明统计范围）**

| 项 | 值 | 来源 / 范围 |
|---|---|---|
| 请求总数 | ~4000（4 轮 × 1000，50 线程） | 压测客户端计数 |
| Redis `cmdstat_get` | 4011 | **Redis `info stats`** |
| `keyspace_hits` / `misses` | 4008 / 5 | 同上 → 命中率 **99.88%** |
| Redis GET 平均耗时 | 3.15 µs | Redis `info commandstats` |
| **商品表查询次数** | **5**（≈4 轮首次 + 1 次手工） | 由 `cmdstat_set=5` 反推 |
| 端到端响应时间 | ~66 ms / ~750 RPS | ⚠️ **受 JDK HttpClient 自身瓶颈影响，不代表服务端能力** |

⚠️ **该结论的边界**：以上只证明「命中缓存时不查**商品表**」。
**不等于**"数据库零压力"—— 内联卖家信息后会引入 `user` 表查询，需另行设计（§3.5）。

## 3. 关键设计约束（**必须先读，含需改代码项**）

### 3.1 商品状态 × 操作矩阵（第 2 点）

| 操作 | `1` 在售 | `0` 卖家下架 | `2` 已售出 | `3` 平台下架 |
|---|---|---|---|---|
| 编辑 `update` | ✅（且无交易中订单） | ❌ `2003` ⁽¹⁾ | ❌ `2003` | ❌ `2003` |
| 卖家下架 `offline` | ✅（且无交易中订单） | ❌ `2003` | ❌ `2003` | ❌ `2003` |
| 删除 `delete` | ✅（且无交易中） | ✅ | ❌ `2003` | ❌ `2003` |
| 重新上架 `relist` | ❌ `2013` | ✅ → `1` | ❌ `2013` | ❌ **`2013`** |
| 管理员下架 | ✅ → `3` | ✅ → `3` | ❌ `2014` | ❌ |
| 公共列表/搜索可见 | ✅ | ❌ | ❌ | ❌ |
| 详情可访问 | ✅ | ⚠️ 待定 | ✅（展示"已售出"） | ⚠️ 展示下架原因（待定） |
| 可下单 | ✅ | ❌ `2003` | ❌ `2003` | ❌ `2003` |

> **⭐ 两道防线，顺序是「先跨表、后同行」**（10.12 D3 实测确认）：
> 1. `assertNotTrading` —— 查 **`orders` 表**有没有进行中订单（待付款/已付款/已发货）→ 命中返回 **`2010`**
>    ① 它**先执行**，所以"刚卖掉、订单还没走完"的商品会先拿到 `2010`（比 `2003` 更精确）
> 2. **CAS** —— 把状态条件写进同一行的 `WHERE` → `rows == 0` 返回 **`2003`**
>
> 跨表条件（`orders` 里有没有单）**塞不进 `product` 的 `WHERE`**，所以两者不可互相替代。
>
> ⁽¹⁾ **⚠️ 待决策**：当前 `update` 的 CAS 是 `.eq(status, 1)`，所以**卖家下架(0)的商品改不了**。
> 实际业务里更顺的流程是「下架 → 改描述 → 重新上架」。两个选择：
> - **A. 维持现状**（只能编辑在售商品，要改就先 `relist`）—— 零改动
> - **B. 放宽为 `.in(status, 0, 1)`**（下架的商品也能编辑）—— 改一行
>
> **这块由你定，我先按现状写在文档里。**

**"交易中"的定义**（D1 已实现）：

```
该商品存在 status ∈ {0 待付款, 1 已付款, 2 已发货} 的订单
→ 禁止 编辑 / 下架 / 删除 / 重新上架
```

### 3.2 ⚠️ 并发保护：不能只靠"更新前查询"（第 2 点核心）

**现状（需改代码）**：`update` / `offline` / `delete` 目前是**三步**：

```
① selectById 查当前状态
② assertNotTrading(id) 在 Java 里判断
③ updateById 更新
```

**①②③ 之间都有时间窗口。** 冒烟测试（单请求）测不出，并发下会漏。

**要求：所有状态类写入必须把约束塞进 SQL 的 `WHERE`（CAS）**

```sql
-- 卖家下架：只有"在售"才能下架
UPDATE product SET status = 0, version = version + 1
WHERE id = ? AND status = 1;

-- 编辑：同样要求"在售"
UPDATE product SET title = ?, ... , version = version + 1
WHERE id = ? AND status = 1;

-- 删除（逻辑删除）
UPDATE product SET deleted = 1 WHERE id = ? AND status IN (0, 1);
```

**`rows == 0` 一律解释为"状态已被别人改过，本次操作不成立"** → 报错（`2007` / `2010`）。

**`assertNotTrading` 保留** —— 它的作用是**给用户友好提示 + 快速失败**，
**但不能作为唯一保护**。两者都要有。

### 3.3 管理员强制下架的边界（第 3 点）

**允许的操作对象**：`status = 1`（在售）或 `status = 0`（卖家下架）
**拒绝**：`status = 2`（已售出）、`status = 3`（已平台下架）、**存在非终态订单（交易中）**

```sql
UPDATE product
SET status = 3, offline_reason = ?, offline_time = NOW(), version = version + 1
WHERE id = ? AND status IN (0, 1);     -- ⚠️ 条件必须在 SQL 里
```

**要求**：

| 要求 | 说明 |
|---|---|
| 拒绝交易中/已售 | 单独查一次非终态订单 → 有则报错（`2010` / `2014`）；**并用 CAS 兜底** |
| 记录原因 | `product` 新增 `offline_reason`（+ 建议加 `offline_time`） |
| 与卖家下架区分 | 卖家下架 = `0`；平台下架 = `3`（状态上就分得开） |
| 卖家不能解除 | `relist` 只接受 `status = 0` → `3` 进不来（§2.1） |
| **不破坏已有订单** | 只改 `product.status`，**不动 `orders`**；已完成订单仍可查、仍可评价 |

### 3.4 订单交付信息：来源与可见性（第 4 点）

### 3.5 ⚠️ 商品详情的缓存范围（第 8 点，容易踩坑）

**问题**：现在 `product:detail:{id}` 缓存的是**整个 `Product` 实体**。
如果 D6 把卖家信息（含**评分**）也塞进去，会出现：

```
卖家收到一条新评价 → 评分从 4.5 变成 4.3
→ 但商品详情缓存 TTL 30 分钟 → 买家最长 30 分钟看到的还是旧评分
```

**正确做法：缓存分层，卖家信息不进商品缓存**

```
product:detail:{id}   →  只缓存 Product 本体（商品自身字段）    TTL 30min
user:brief:{id}       →  UserBrief（昵称/头像/校区/评分/评价数）  TTL 【60s，单独设】
```

- 卖家改名 / 收到新评价 → **最多 60 秒**后生效（而不是 30 分钟）
- 装配发生在 `getDetail` 返回前（读商品缓存 + 读卖家 brief 缓存）

**⚠️ 绝不能把卖家信息塞进 `product:detail:{id}`。**
**⚠️ 也不能不缓存 `user:brief`** —— 否则每次详情请求都会查 `user` 表，
§1.4 那个"4000 次请求只查 5 次"的结论**就不再成立**（会变成 4000 次 user 查询）。

**⚠️ 连带的结论边界**（用户要求注明统计范围）：
§1.4 的压测数据**只覆盖商品表**，内联卖家信息后必须**重新理解这些数字**。
